# Historical record imports

In Settings → Historical record imports, download the fictional JSON template or choose a board record export. The file can contain up to 1,000 opportunities and be up to 8 MB. Split larger files before import. Supported roots are version 1 `opportunity-board-records` or `opportunity-knox-historical`, or an object containing an `opportunities` array. `company` and `role` are required. Use the template's stage IDs and ISO timestamps; keep date-only deadlines as YYYY-MM-DD. Date-only timeline corrections and stage-entry dates from existing exports retain their date-only values. Beyond identification, provide `stageEnteredAt` or a dated timeline event for the current stage. Missing creation dates are explicitly reported and use import time.

## Review and apply

1. Preview the file. No opportunities, tasks or documents change. Source previews are private persisted metadata; five pending previews are retained and apply tokens expire after one hour.
2. Review source details/history and duplicate reasons. Matches use source IDs, exact normalized record-field hashes, declared JD hashes, tracking-normalized job URLs, employer/job reference and employer/role. Matching a CV shared across jobs is not a JD duplicate signal. Manifest hashes are supplied metadata, not verified imported file bytes. Repeated employer/role pairs can be separate applications. At most 25 strongest existing candidates are shown per row; within-file matches are flagged.
3. Each row starts skipped. Create a separate opportunity, or choose an existing candidate. Select individual differing fields to replace. Timeline and communications/interview history and the current stage/outcome are separate explicit choices. Only selected fields change; history is appended and exact matching entries are deduplicated. Original effective timestamps, date corrections and activity revision snapshots are retained. Imported active record/event/activity IDs are regenerated.
4. Confirm the choices. A verified full backup must succeed before all record changes and the receipt are committed in one SQLite transaction. Missing managed files stop the backup/import. Record/document/task edits after preview, an expired or replaced preview, or an unreviewed merge target block application. Preview the file again after a conflict.
5. Completed imports show created/merged/skipped counts and the backup name. Download the import report and original source records/linked manifest/tasks. Reports and source archives persist across restart and are included in full backups and JSON record exports. An identical applied file shows its previous receipt and cannot create duplicates by retrying. Skipped rows are final for that file; use a new subset file to review those records later.

## Scope and preservation

This is a record-only workflow. It activates opportunity details, timeline and interview/communication history. Native offers, reviews, application packs and other record extensions remain in the original source archive. Linked task records and document manifests are archived, with no file bytes copied or tasks created. Current activity attachment IDs are cleared; original IDs remain in source/revision snapshots for reference. Foreign storage paths are never resolved and cannot overwrite or rebind files. Existing target documents, approved/submitted packs, review/offer history and unselected fields remain unchanged.

Settings, authentication, AI keys, chats, assessments, standalone Buddy data and unrelated source-library records are not imported. No model call or automatic review is queued. Use full backup restore for a complete workspace with managed files. CSV imports, arbitrary folder-to-opportunity extraction, native pack activation and task reconciliation are outside this increment. Original uploaded file bytes are not retained: the report preserves parsed source records and linked manifest/tasks, not the full workspace export.
